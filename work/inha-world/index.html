01 · Problem

Build a world, not a one-off demo.

A virtual campus starts as a rendering problem, but quickly becomes a product-systems problem: movement, streaming, rooms, NPCs, quests, maps, accounts, settings, content tools, persistence, deployment, and regressions all have to coexist without making each release fragile.

02 · Product system

One public repository, multiple product surfaces.

Design→Implement→PR→CI / Browser QA→Production→Readback

The repository is structured as a public monorepo. INHA WORLD lives under apps/world, alongside database migrations and tests, verification scripts, editor/studio tooling, serverless handlers, an NPC factory, and asset conversion utilities. The World prioritizes WebGPU with a WebGL2 fallback.

03 · Verification architecture

Regression prevention is part of the product.

Protected main verify required

Changes to main go through pull requests and the required verify check.

Public CI public-ci + public-db

The verify job runs static/unit/build checks and a disposable Supabase replay with database verification.

Browser QA many focused workflows

Dedicated browser checks cover world stability, photo mode, maps, rooms, UI focus, inventory, models, and more.

05 · Key decisions

Treat shipping as a chain of evidence.

  • Separate public development from production secrets. The public repository contains development code and reproducible checks, while production credentials and operational overlays remain separate.
  • Protect main with a required verification gate. The repository contract makes regression checks part of normal change flow rather than a cleanup step.
  • Use focused browser workflows for fragile surfaces. High-risk interactions receive targeted browser QA instead of relying only on a monolithic smoke.
  • Verify the deployed source. A release is not treated as complete until Production is READY and its Git SHA can be tied back to the intended main revision.
